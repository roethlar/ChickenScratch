# s3-8: Metadata is left out of the identifier and link analysis

**Severity**: MEDIUM — existing links change destination or stay unresolved
**Status**: Verified — accepted 2026-10-27 23:09 UTC

## Evidence
`crates/core/src/core/compile_links.rs` `scan` walks `blocks` only. With `% [Title]{#same}` as a title block, a body heading `{#same}`, a bare `#same` link and a document link, the kept-duplicate rule sees one `same`, renames the heading and redirects the bare link to it while the title keeps `same`; today's HTML destination was the title. A root-anchored document link appearing only in metadata does not fire the gate.

## Approach
Include `meta` in the scan (identifiers and links), as generated content outside every section.

## Files changed
Declared before repair: `crates/core/src/core/compile_links.rs`, `crates/core/tests/compile_links.rs`. Repair: the same two files.

## Guard proof
`metadata_identifiers_and_links_take_part` fails with the metadata walk removed (`&Value::Null` in place of `root["meta"]`); restored → 13 passed.

Repair `fbb507e`: `meta` and a MetaMap's content are walked as maps by position (`visit_meta_map`); nothing is inferred from keys. `metadata_keys_named_t_do_not_hide_the_rest` (root-level `t` beside a duplicated title identifier; title-only document link beside `t`; `t` inside a nested map next to a shared identifier) fails with maps holding a `t` key skipped ("both `same` kept despite a `t` key"), exit 101; restored → 15 integration and 7 unit tests passed, core clippy and fmt clean.
